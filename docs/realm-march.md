# 新区服出征与恢复

本页说明已实现的 RocksDB 新区链路。`realm serve` 在原卷恢复日志水位并启动到期扫描后受理网关命令。一区一账号目前对应一个角色，以认证账号为执行键；客户端和行军到期任务进入同一玩家队列，首次访问时加载，后续命令复用内存中已提交的版本。独立的 Battle Worker 在玩家邮箱外计算；战损和返城在所属玩家邮箱内提交。GAME 的独立线程按已提交日志更新 MySQL；跨玩家调度列入后续任务。

## 启动与验证

用 [`volume init`](../README.md#新区服数据卷) 创建独立卷后，向新区 GAME 提供与所连网关一致的 `SLG_TOKEN_SECRET`（至少 32 个 UTF-8 字节）。下例沿用建卷时的 shell 变量。GAME 独占该卷。正常启动需提供[投影账户与地址](mysql-projection.md)，纯临时卷演练可显式设置 `SLG_PROJECTION_ENABLED=false`。

```bash
SLG_GAME_RPC_PORT=19082 SLG_GAME_PORT=18082 \
  java -jar "$game_jar" realm serve "$SLG_REALM_DIR" "$SLG_REALM_ID" "$SLG_REALM_VOLUME_ID"
```

网关设置 `SLG_GAME_RPC_TARGET=127.0.0.1:19082`，从 UC 获取的会话仍由网关和 GAME 分别验签。健康探针 `GET /health` 在健康端口返回区服、卷 ID 和已提交日志末序号，日志标记不可用时返回 503。GAME 就绪无需等待 MySQL 游戏投影库可达；本阶段未提供自动路由或跨机器接管。独立[强杀重启检查](../scripts/check-realm-march.py)使用临时会话快速验证；[MySQL 集成验收](../scripts/verify-mysql.py)在一次性 MySQL 上启动真实 UC，通过 Gateway 注册、登录再执行同一恢复场景。

## 首次加载与驻留

UC 登录负责签发账号令牌。首次进入新区时，客户端可以调用 `GetPlayerAsync`；该请求以及其他已认证的 GAME 命令使用同一玩家目录。冷加载期间，本玩家的请求留在自己的有界队列里。加载线程从原卷读取并解码角色；完成后，由业务线程按受理顺序执行命令。加载 A 时，已经驻留的 B 仍可执行业务。如果所有加载线程都在忙，其他尚未驻留的玩家会排队。加载出错返回 `PLAYER_LOAD_UNAVAILABLE`，这批命令都未执行业务，可使用原 ID 重试。

加载器先在短锁内取得同一时刻的区服日志水位和 RocksDB 快照，再在提交锁外执行磁盘读取。这样 A 的慢读取不会占住 B 写日志需要的锁。关卷要等快照释放；若读取期间区服写入结果变得不明，加载器不会把旧值交给业务线程。

快照包括版本、兵力、英雄和活动行军 ID。首次建角也使用同一入口；原卷读取“尚未建角”后，只有建角批次写成功才发布新玩家。出征的兵力和英雄由当前快照判定；批次提交后才替换快照、回复客户端。GAME 按永久角色 ID 和请求 ID 读取原卷独立的回执键，按行军 ID 读取行军记录。旧回执重试不会把新兵力改回去；版本冲突、提交结果不明或发布失败会使该对象失效，必须重新加载。区服写入结果不明时仍按原卷恢复协议停写。

此阶段按**业务活动**驻留，TCP 连接空闲期间也可回收玩家内存。只有没有排队命令、加载和在途提交的对象可以退出。空闲超过期限会回收；驻留名额已满时优先回收最久未访问的空闲对象。一个长时间静默但仍在线的玩家可能需要在下一次命令时重新加载，未完成的行军和任务继续保存在卷中。

| 环境变量 | 默认值与含义 |
| --- | --- |
| `SLG_REALM_LOAD_WORKERS` | 最多 4 个加载线程，默认取 4 与业务线程数中的较小值；可设 1–32。 |
| `SLG_REALM_MAX_RESIDENTS` | 16,384 个玩家目录名额，包括加载中的账号。没有空闲对象可回收时拒绝新的激活。 |
| `SLG_REALM_PLAYER_IDLE_SECONDS` | 300 秒。闲置玩家由维护线程回收。 |
| `SLG_GAME_QUEUE_CAPACITY` / `SLG_GAME_ACCOUNT_QUEUE_CAPACITY` | 默认全区 512、单账号 16 条在途/排队命令；超过预算返回 `SERVER_BUSY`。 |

健康探针的 `players` 显示 `residents`（当前驻留）、`loading`、`running`、`outstanding`、累计 `loads` / `loadFailures` / `evictions` / `rejected` / `expired`。这些是整个新区的计数，不按玩家打监控标签。

玩家断线后可凭原请求 ID 查询出征回执。GAME 从已认证会话定位角色，用该角色和原请求 ID 在原卷读取回执。查询和派兵共用一个账号邮箱。另一个连接上的原请求可能尚未进入邮箱，此时查询只反映本次读取看到的状态，重发仍需沿用原 ID。[断线查询示例](api.md)

## 接口与规则

Unity 在已认证的 TCP v2 连接上先建角，再出征。每个操作都携带自己的请求 ID。[客户端协议](api.md)

```csharp
CreatePlayerRsp created = await client.CreatePlayerAsync("create-1",
    new CreatePlayerReq { Name = "Alice" }, cancellationToken);
StartMarchRsp departure = await client.StartMarchAsync("march-1", new StartMarchReq {
    TargetX = 150, TargetY = 150,
    Troops = { new TroopGroup { Type = TroopType.Infantry, Count = 120 } }
}, cancellationToken);
string marchId = departure.March.MarchId;
```

| 命令 | 当前行为 |
| --- | --- |
| `CreatePlayer` | 初始 T1 步兵 3,000、矛兵 1,000、射手 1,000，英雄 `sergey`。初始位置固定为 (0,0)。 |
| `GetPlayer` | 返回该玩家的可用兵、累计伤兵 wounded、阵亡 dead、英雄的 `assignedMarch`、活动行军 ID 和玩家状态版本。 |
| `StartMarch` | 任务默认采集，目标可选 (150,150)、(650,650)、(1150,1150)。攻击 NPC 的目标为 (120,120)、(600,600)、(1100,1100)。每人最多三支活动行军，可选 T1 三兵种。默认带 `sergey`，显式传空 `HeroSelection` 可不带英雄。`StartMarchRsp.March` 返回行军 ID、服务端出发与到达时间及任务 ID 等首次出征结果。 |
| `GetMarch` | 传 `GetMarchReq.MarchId` 查询自己的行军；他人的 ID 与不存在的 ID 返回相同错误。 |
| `RecallMarch` | 传 `RecallMarchReq.MarchId` 召回自己的出征或采集队伍。原任务取消，创建唯一返城任务；同 ID 重试返回原回执。若阶段已到期，先补做该阶段再判定能否召回。已经开始返城或准备战斗时不会重复建返城任务。 |
| `GetBattle` | 传 `GetBattleReq.BattleId` 查询自己的战斗。NPC 的战斗 ID 等于行军 ID；返回输入摘要、规则版本和状态。待计算时 result 为空，结算后返回完整结果。 |

## 到达、返城与离线恢复

以 120 名步兵去 (150,150) 采集为例，出征后城内暂有 2,880 名步兵，英雄指向该行军。三个阶段都有持久化的任务：

| 到期任务 | 行军变化 | 此时交付的内容 |
| --- | --- | --- |
| `MARCH_ARRIVE` | `OUTBOUND → GATHERING` 或 `RETURNING` | 矿空闲时，同批建立占用和 3 秒采集待办。矿已被占时，同批完成到达并建空载返城任务。 |
| `GATHER_DONE` | `GATHERING → RETURNING` | 核对占用的行军、玩家与任务代次，释放矿点，把 120 × 5 = 600 木材记在行军货物上，建立返城任务。 |
| `MARCH_RETURN` | `RETURNING → COMPLETED` | 同一批次标记任务完成、归还 120 名兵、释放英雄与队列槽位、将 600 木材加入 `resources.WOOD`。 |

定时器按到期时间、任务 ID 分页读取 RocksDB 索引；索引和任务状态在同一写批次更新。每个账号最多一个定时工作在途，即使被驱逐或没有客户端连接，也会从原卷加载。玩家队列满时暂缓投递，原任务仍为 `PENDING`。执行前重新核对所属玩家、当前任务 ID、代次、到期时间与行军阶段，已完成或已取消的旧投递不会再次生效。确定性坏任务标 `BLOCKED`，保留原因、预留兵和资产供诊断。存储暂不可用则保留原任务重试。

下一阶段从上一个任务**原定到期时间**开始计时。例如 GAME 停机超过整个采集行程，重启会分批补做到达、采集和返城，不需要玩家登录，也不会从重启时间重新等待整段旅程。`SLG_REALM_TIMER_BATCH` 控制单页条数和在途玩家数，默认取 16 与命令总容量中的较小值，可设 1–1024。`/health` 的 `tasks` 显示扫描健康、在途玩家、投递、生效、重复或过期、暂缓以及异常计数。

### 两人争同一个矿

出征只预留自己的兵和英雄。到达、采集完成、召回可能同时影响同一个矿，执行时要同时轮到玩家和目标矿点。扫描器按到期时间和任务 ID 登记到达；玩家冷加载速度不能颠倒已登记的同矿到达。召回在玩家队首解析目标，也要遵守同矿执行顺序。第一支成功提交占用的行军开始采集，其余记录 `MARCH_TARGET_OCCUPIED` 并空载返城。后到者的原出征回执仍有效。

矿点以 `resource:150-150` 这样的对象键保存占用行军、所属玩家和采集任务代次。占用、释放与行军和待办同批提交。采满或主动召回释放矿点后，下一支队伍即可占用，无需等上一支到家。空闲对象保留版本，迟到的旧采集任务不能释放新主人。MySQL 投影在同一序号更新行军和矿点。

每个矿使用与单玩家相同的有界队列预算，等待时不占业务线程。扫描器也限制同一矿占用的在途名额，已满就留下持久待办供下轮投递。健康指标 `players.targets` 和 `players.targetRejected` 分别记录正在协调的目标队列数和累计目标容量拒绝数。重启重新扫描持久待办，进程内尚未执行的排队次序不持久化。

GAME 在开放请求前分页核对每个待完成的采集任务。行军、目标矿点、占用人、任务代次和采集规则必须一致，任一项不符就停止启服。运行中，采满和召回会再次检查归属，避免把矿点释放给错误的行军，或在失去占用后发奖。[采集点检查](../slg_game/src/main/java/com/slg/game/realm/GatherSite.java) · [争矿强杀验收](../scripts/check_realm_mine.py)

### NPC 到达与战斗

对 `ATTACK_NPC`，到达会将行军置为 `BATTLE_PENDING`，同批保存固定参战输入、种子、规则版本及输入摘要，保留已派出的部队和英雄。GAME 从原卷的待计算索引分页取任务，通过复用的 gRPC 通道发送给独立 Worker。RPC 期间玩家仍可查询、发起其他合法操作。Worker 返回后，GAME 重新进入玩家邮箱，核对战斗 ID、输入摘要、版本、攻守方、每组数量与伤亡守恒，以及行军阶段和预留。一次本地提交同时写入战报、伤兵 / 阵亡记录、幸存者、胜利货物与返城待办，并移除待计算索引。战报仍保存在原卷。

胜利时随军携带木材 500、食物 500、宝石 10，到家后才计入玩家资源。失败或平局没有胜利货物。即使全军覆没，返城待办仍释放占用的英雄和行军槽位。Worker 不可用或结果无效时，GAME 保留待办、预留和固定快照，退避重试。同一结果再次送达不会再次记伤亡或发奖。GAME 的 `/health` 中 `battles` 提供 `inFlight`、`submitted`、`settled`、`failedAttempts` 和 `lastFailedBattle`。

## 原子提交与故障语义

- 新建卷使用格式 8 保存强类型玩法回执，前缀清理后的对应格式为 9。GAME 启动时先校验登记的卷格式和身份，再核对日志水位及在途任务。原有开发卷仅用于只读观测。
- 一次 WriteBatch 提交连续日志序号、确定的业务事实、受影响对象的新版本和原请求回执。出征变更包含玩家（扣兵和英雄占用）、行军和到达任务。重放事实时可以使用记录里的数据和规则版本，无须按新时钟重算。
- 唯一键为本区的“角色 ID + requestId”；摘要绑定原操作和请求内容。相同请求直接返回原结果，即使状态已变化。同 ID 换参数返回 `REQUEST_CONFLICT`。已识别写命令的确定性业务拒绝也会记录，使用原 ID 重试仍得到该拒绝。
- 任一对象预期版本不符，整个写批次不生效、不推进日志；返回 `STATE_CHANGED` 时可用原 ID 重试。底层写入结果不明时停止本卷后续提交，回包按结果未知处理；重新打开同一原卷后，以回执和恢复后的水位判断。此承诺只覆盖 GAME 进程退出、原 OS 和卷保留。
- 常规新区保留全部业务日志和回执，只读预演报告安全边界。隔离测试卷可实际清掉前缀，格式 9 用已清水位 F 区分合法清理和意外缺号，重启时核对从 F+1 到 H 的每条保留日志。回执、行军与待办有独立键；原出征日志已经清掉时，GAME 仍可取回原结果并完成一次返城。这一验收覆盖正确性，峰值吞吐另行压测。[保护与清理验收](journal-retention.md)
