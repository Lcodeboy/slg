# 磁盘保护、日志预演与隔离清理验收

磁盘余量决定是否受理新操作。历史日志的保留边界由消费和恢复证据决定。在线 GAME 和观测命令只报告候选范围。实际删除入口只编译进集成测试，且只接受测试自己在临时目录创建的新卷。

## 磁盘保护

后台每 5 秒读取**登记原卷目录所在文件系统、本进程可用的字节数**。同一文件系统上其他程序的用量也会影响这个数。提交锁内只读取内存样本和单调时钟。默认告警线为 2 GiB，硬线为 1 GiB，须按实际峰值写入量、压缩放大和全部在途任务的完成成本重新定标。

| 条件 | 对新客户端写入的影响 |
| --- | --- |
| 健康样本，余量大于等于告警线 | 放行；之前硬限或失联的保护也在这里解除 |
| 首次或正常运行后进入两线之间 | 告警，继续放行 |
| 余量小于等于硬线 | 返回 `DISK_PRESSURE` |
| 未取得样本、采样失败或样本满 15 秒 | 保守暂缓；触底或失去观测后，仅回到两线之间时仍处于恢复等待 |
| 查询、重发已确认请求、推进已受理待办、处理已返回的战果 | 继续原有路径；已经发生的真实 I/O 错误仍由区服存储的故障机制处理 |

剩余空间是采样值，硬线为已受理的返城、战损、回执等工作留出余量，无法保证其他程序不会在两次采样间把磁盘用尽。监控字段位于新版 GAME 的 `GET /health` 的 `disk` 下。[准入与采样](../slg_game/src/main/java/com/slg/game/storage/RealmDiskGuard.java)

## 怎么算候选的最后一个序号

所有序号均为**闭区间**。F 是卷上已清理的最后一个序号，完整历史卷的 F 为 0。H 是本次读取的原卷水位，K 是最近保留条数（配置 `SLG_REALM_JOURNAL_KEEP_ENTRIES`，默认 10,000），S 是独立快照经恢复演练证明的覆盖水位，c 是每个必需持久消费者已确认的连续游标。所有证据必须属于同一区、同一卷。

| 上界 | 为什么需要它 |
| --- | --- |
| 已核验的连续日志 | 必须能逐条从 F+1 正确读到 H。首末键不符、中间缺号、内容损坏或检查仍在进行，就暂停预演 |
| H − 1 | 当前 GAME 重启会用最后一条业务日志验证水位，即使其他条件全满足也要保留 JH |
| H − K | 保留最近 K 条供重放和排障。这个窗口按条数计算，不代表按天保留 |
| 每个消费者的 c − 1 | MySQL 重启时需要重新读取 **Jc** 验证 SQL 已归档的内容。即使 MySQL 已确认到 c，也只能把 c 前面的记录列为候选 |
| S | 已验证快照能恢复到 S，并能从 S+1 接着重放。单有备份文件、卷 UUID 或一个手填数字都不算恢复证明 |

取上述上界的最小值 B，负数按 0 处理。如 B>F，候选为 **[F+1, B]**。例如 F=0、H=100、K=20、MySQL 游标=80、验证过的快照覆盖到 70 时，候选为 **1–70**。如果另一个必需消费者只到 60，范围缩为 **1–59**。每次加持久消费者，都要把它登记为必需项。本阶段唯一上线的持久消费者是 MySQL。

- **CANDIDATE**：证据齐全且上界大于 F，报告列出 `firstEligibleSeq`、`lastEligibleSeq` 和限制它们的因素。只涉及 `J` 业务日志，玩家状态、请求回执、任务、引擎 WAL 各有独立生命周期。
- **NO_CANDIDATES**：证据齐全但安全前缀为空，例如游标刚到 1，或全部记录仍在保留窗口内。
- **BLOCKED**：快照缺失或演练失败、S<F、消费者失联／错卷／归档不符、游标超前或退回已清区间（F>0 且 c≤F）、原卷有缺号或不能读取。两个候选序号均为 null。报告中的 `bounds` 只是已知条件。[边界计算与停止条件](../slg_game/src/main/java/com/slg/game/storage/JournalRetentionPreview.java)

## 如何运行

新版 GAME 的 `GET /health` 返回 `journalRetention`。后台分批校验追加日志，探针读取缓存，不会每次请求都扫描全卷。在线进程没有经演练的独立快照时，报告会写明 `VERIFIED_SNAPSHOT_MISSING`。

对已有 GAME 可使用新工具单独观测，无需重启原进程。它在临时目录打开 RocksDB 次实例，只追赶一次，然后固定原卷水位；核对本机 GAME 和 MySQL 的身份、消费状态与对应归档。命令不初始化新卷、不升级格式、不写 SQL 游标。存在错误时看 `state` 和 `blockers`，命令成功返回报告只表示预演已执行。

```sh
python3 scripts/preview-realm.py
# 当线上进程仍使用旧包，可为独立观察器提供新构建的 GAME 包：
python3 scripts/preview-realm.py --jar /path/to/new-game.jar
# 仅当已有独立 checkpoint 且明确准备在临时空间执行恢复演练时：
python3 scripts/preview-realm.py --checkpoint /path/to/independent-checkpoint
```

可选的恢复演练只在新建的临时目录中重放已确定的业务事实。核对区服、卷身份、快照水位和重放后的状态/日志/回执/索引；任何一步失败都会阻断候选。开发原卷的日常观察不提供 checkpoint 参数。[只读命令](../slg_game/src/main/java/com/slg/game/storage/RealmVolumePreview.java)

## 隔离验收

构建后运行 `python3 scripts/check-realm-disk.py`。它在临时卷中先派兵，再只调整测试 GAME 的阈值以触发硬限，最后恢复正常阈值。验收会核对新写暂缓且不占日志序号、同一出征回执仍可读取、三项待办继续完成，以及原请求 ID 在恢复后只提交一次。[磁盘故障场景](../scripts/check-realm-disk.py)

`python3 scripts/verify-mysql.py` 包含真实 MySQL 的正向预演用例：独立 checkpoint 在 1，原卷高水位为 3，MySQL 游标在 2，最近保留 1 条。这时返回候选 **1–1**；随后核对原卷三条日志仍在、SQL 仍停在 2。移除快照证据后，同一条日志也不再列为候选。[集成测试](../slg_game/src/test/java/com/slg/game/projection/MySqlProjectionStoreIT.java)

### 隔离卷的真实清理与强杀

同一脚本还有一项实际清理测试。它使用随机卷 UUID、独占 RocksDB 写者和本轮一次性 MySQL 中的独立 schema。测试构建可放在独立项目副本中运行，以免干净构建覆盖在线 GAME 使用的包。

| 时点 | 必须观察到的结果 |
| --- | --- |
| 清理前 | J1 建角、J2 出征、J3/J4 是已持久化的业务拒绝。H=4，checkpoint 实际恢复到 S=4，最近保留 K=1。MySQL 只提交到 c=3。 |
| 执行清理 | 取不到本次 SQL 证据时，J1、J2 仍在。健康路径在同一事务锁住游标、比对 J3 归档指纹，安全上界为 `min(3,3,2,4)=2`。提交后直接读原始键，J1/J2 已消失，J3/J4 和序号 2 的出征回执都在，SQL 仍为 3。另有用例验证同序号但不同内容的 SQL 归档也会阻断删除。 |
| 清理批次刚返回 | 在 RocksDB 写句柄仍打开时强杀测试写进程。正常 GAME 从同卷重启，以 J3 校验 SQL 后追到 4。此时行军仍在去程，120 名步兵在外、城内 2,880，测试随后强杀这台 GAME。 |
| 在途重启和结算后重启 | 正常 GAME 无需玩家命令即完成到达、采集、返城。结算后强杀并重启，再用原 ID 经 gRPC 重发出征。完整回执相同，原卷和 SQL 均停在 7，SQL 中只有一条返城事实；角色、行军和三个任务的状态与版本逐项相符。 |

删除只覆盖业务键 `J1..J2`。范围墓碑、格式 9 和 `F=2` 在开启 WAL 的同一 WriteBatch 中提交。GAME 重启要完整核验 `J(F+1)..JH`，缺键或内容损坏就拒绝就绪。回执有独立键，所以即使 J2 已清掉，重试仍取得原序号和原结果。范围墓碑使这些业务键不可读取，SST 文件何时释放空间取决于后续压缩。

这项实验只执行首轮清理。当前恢复演练需要从 J1 重放以证明快照内容；已有前缀被清后，它无法独立证明下一份快照，必须停止。连续多轮清理需要可验证的快照证明链。格式 9 的 GAME 重启按页核验全部保留日志，启动耗时取决于保留量，本次小卷实验没有测量生产规模下的恢复时间。[隔离执行器](../slg_game/src/test/java/com/slg/game/storage/IsolatedCleanupVolume.java) · [跨进程故障断言](../slg_game/src/test/java/com/slg/game/storage/CleanupCrashScenario.java)
