## Unity 游戏连接（2026-11-06）

Unity 的七个玩法接口均由协议生成，公开消息号只在对应操作的协议方法上登记。TCP 帧版本为 2，Gateway 内部调用 `GameRpc.Play`。建角、出征和召回的回执区分成功类型和错误分支。正常 GAME 使用格式 8/9 的卷；已有开发原卷仅作只读观测。[客户端接口](api.md) · [C# 验收与运行方法](../clients/unity/README.md)

Gateway 分别监听账号 HTTP 和游戏 TCP 端口。游戏连接绑定已验签会话，支持 Protobuf 命令、回执、心跳和重新鉴权。已用真实套接字验证拆包与连续多帧、证书校验、命令等待期间的并发拒绝和断线后的 gRPC 预算释放。公网游戏入口须配置 TLS。[网关验收](../slg_gate/src/test/java/com/slg/gate/GatewayServerTest.java) · [Unity C# 接入说明](../clients/unity/README.md)

C# 客户端已按 .NET Standard 2.1 编译，并在隔离环境通过 TLS 接入真实 Java Gateway、调用受控 gRPC GAME。正确的证书链获准，错误的根证书被拒绝。客户端空闲 62 秒后仍能通过同一连接执行命令，超过网关 60 秒读空闲断开的门槛。原生 Android / iOS 的 IL2CPP 真机联调仍待完成。

四进程隔离验收从 UC 注册、登录开始，经 TCP 出征，强杀 GAME 后从原卷恢复，只返还 120 名步兵、发放一次 600 木材。在独立 MySQL 停机的场景里，重连后能查回 J3 的原出征响应，恢复的 MySQL 最终追到 J7。另用 8 条长连接执行了 100 条混合命令。单区万人在线的容量验收仍待进行。[行军恢复](../scripts/check-realm-march.py) · [投影停机验收](../scripts/check_realm_projection.py) · [压测参数与结果](high-load-design.md)

## 断线查询行军回执（2026-11-06）

在隔离卷上分别于出征写入前、提交后未回包时终止 GAME。重启后先按原请求 ID 查询，两次分别查不到回执和取回包含原行军 ID 的出征响应。另一次演练在 J2 出征后实际清掉 J1、J2，再强杀在途 GAME。恢复到 J7 后查询仍返回 J2 的原始出征响应，120 名步兵返城、600 木材到账各一次。[提交边界](../slg_game/src/test/java/com/slg/game/realm/RealmMarchRecoveryTest.java) · [已清日志的回执查询](../slg_game/src/test/java/com/slg/game/storage/CleanupCrashScenario.java)

此前的四服务验收覆盖了断线查询建角响应。投影停库场景又验证了 GAME 重启后查询成功、已拒绝、积压暂缓的三个请求，分别取回原出征响应、原错误和未产生回执的查询结果，三次查询前后日志序号都是 6。MySQL 恢复后追到 7。本轮 169 项常规 Java 测试和 25 项 MySQL 集成测试通过。[停库验收脚本](../scripts/check_realm_projection.py)

## 故障与容量边界

承诺范围为 GAME 进程崩溃且原操作系统和原卷仍可读取。RocksDB WAL 开启，业务写批次使用 `sync=false`。GAME 结果不明时停止向该卷继续写入，重开同一卷后通过回执判定。NPC 派发失败只延迟该战斗；稳定业务 ID、保存的输入和系统回执保证重算可重复、结果只生效一次。

目前支持单账号的 NPC 结算和多个玩家争同一采集点。一次操作同时修改多个玩家、PVP、地图 AOI 推送、服务发现和接管尚待实施。城建、训练、治疗和联盟等玩法需要在区服提交机制下接入。单区 10,000 在线、峰值 2,000 命令/秒需要混合负载验证。[容量验收方案](high-load-design.md) · [生产任务顺序](production-task-plan.md)

## MySQL 投影验收（2026-11-05）

MySQL 8.4.13 实际停库时，SQL 游标停在 1。通过网关发起采集后强杀 GAME，在数据库离线时从原卷重启，120 名士兵返城，600 木材只到账一次。数据库恢复后投影追平到 6；此前因积压暂缓的请求沿用原 ID 得到业务结果，游标推进到 7。再重启 GAME 并重发出征请求，SQL 仍是连续的 7 条决定，角色、行军和任务快照逐项匹配原卷。故障场景使用专用投影账号，测试结束回收了临时容器及匿名卷。

干净构建通过 118 项常规 Java 测试、8 项真实 MySQL 集成测试（其中 7 项专测投影）；36 项 Python 工具测试通过。投影测试覆盖完全重复与部分重叠的批次、并发消费者、提交前后确认中断，以及遇到缺号、错卷、分歧归档或无法表示的数据时停止推进。[运行说明与故障脚本](mysql-projection.md)

## 磁盘保护与日志预演验收（2026-11-05）

在现有开发 1 区只读打开次实例，业务日志从 1 连续到 5，MySQL 游标为 5，文件系统可用约 50.4 GiB。未提供已恢复验证的独立快照，默认窗口还要求保留最近 10,000 条，最终候选为空。前后核对业务文件哈希和水位一致，开发进程继续使用原运行包。

隔离测试卷验证了硬限下的读、同 ID 回执、返城及恢复后的重新受理。另一个临时卷上，用独立 checkpoint 真正恢复并重放，得到候选 1–1 后确认序号 1 仍在；缺口、错卷、坏值和缺失恢复证据均会阻断预演。[实现与复验步骤](journal-retention.md)

## 隔离卷实际清理验收（2026-11-05）

在一次性 MySQL 上把游标固定在 3，原卷写到 4。独立快照恢复到 4，保留窗口设为 1。实际删除仅覆盖 J1 和出征记录 J2，J3、J4 仍可读取。SQL 无法连接时全量保留；单独把 SQL 的 J2 换成另一份同序号内容时，即使快照有效也拒绝清 J1。

清理后强杀仍持有写句柄的进程，正式 GAME 恢复并追平至 J4。经 gRPC 重发原出征取得原回执，查询行军仍在去程，城内有 2,880 名步兵。到达前强杀这台 GAME，继任 GAME 无需客户端命令即完成采集返城。结算后再强杀并重发原请求，原回执仍指向序号 2，原卷和 SQL 均停在 7。七条 SQL 业务事实中只有一次返城，三个待办均已完成，玩家归还 120 人、到账 600 木材。核对了玩家、行军和三个任务的对象版本及完整状态。[跨进程验收](../slg_game/src/test/java/com/slg/game/storage/CleanupCrashScenario.java)

开发 1 区另走只读观察，F=0、J1–J5 连续、MySQL 游标 5；缺少已验证的快照，候选为空。观测前后原卷业务文件摘要一致。验收范围为单卷首次清理与 GAME 进程崩溃恢复。多轮快照证明和压缩后的实际空间回收仍待验证。

## 两名玩家争同一个采集点（2026-11-05）

两个测试账号通过真实 Gateway 并发向 (150,150) 派出 120 和 80 名步兵。J6 时第二支队伍已开始采集，第一支队伍空载返城。核验 GAME 在采集截止时间前被强杀，SQL 中矿点版本为 1，记录的矿主、行军与任务代次一致。

重启同一测试卷后，后台自行追到 J9。双方城内步兵都恢复到 3,000，80 人队伍获得 400 木材，另一方为 0。两人重发原请求都取得原回执。随后原败者重新派兵，成功获得 600 木材。原卷与 MySQL 最终同在 J13，矿点已释放，版本为 4。按行军逐一核对，每次返城与收益仅入账一次。这项测试允许任一队先占矿。[可复跑的断言](../scripts/check_realm_mine.py)

另用隔离卷覆盖了召回释放、旧定时任务迟到，以及矿点归属与代次不一致时停止；调度测试覆盖同矿顺序、热矿满额、不同矿推进和取消/超时释放。本轮范围是单区的一名玩家和一个矿点。AOI 推送、多个玩家共同修改和容量指标另行验收。

## 玩家与采集点专用投影（旧身份基线，2026-11-06）

MySQL 8.4.13 的一次性测试库完成了 001 → 002 升级。已有 129 条玩家记录时，回填跨过 128 行的分页边界；再次执行迁移后，记录数、版本、来源序号和原消费游标均一致。另让旧投影写者在安装两个触发器期间建角并更新角色，并让正常写者与回填在同一区服游标上实际竞争，最终两张新表都读到最近提交的版本。错引擎、游标缺少末条归档、同版内容分歧、来源不明的专用行或矿主字段矛盾时，测试均验证了停止条件。[专用表集成测试](../slg_game/src/test/java/com/slg/game/projection/PlayerResourceProjectionIT.java)

真实争矿时，在 J6 强杀 GAME 后，按矿点坐标和玩家查询都能找到同一个占用者。重启后的复采至 J13，专用表中矿点已释放、版本为 4，完整快照与区服水位吻合。另在 MySQL 停机后从 J1 追到 J7，按账号查到的玩家版本与原卷一致。独立 Compose 新库运行初始化后，又执行两次已有卷的补建，验证 GAME 账号可读专用表且直接 UPDATE 会被拒绝。
